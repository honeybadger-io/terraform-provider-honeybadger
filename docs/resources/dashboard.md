# honeybadger_dashboard (Resource)

An Insights dashboard: a project's grid of widgets charting queries, errors, uptime, check-ins, deploys and alarms. Required scopes: `dashboards:read`, `dashboards:write`.

## Example Usage

```terraform
resource "honeybadger_dashboard" "ops" {
  project_id = honeybadger_project.app.id
  title      = "Operations"

  widgets = jsonencode([
    {
      id           = "error-rate"
      type         = "insights_vis"
      grid         = { x = 0, y = 0, w = 6, h = 3 }
      presentation = { title = "Errors in ${honeybadger_project.app.name}" }
      config = {
        query = "filter event_type::str == \"notice\" | stats count() as count by bin(1h) as time"
        vis   = { view = "line", chart_config = { xField = "time", yField = "count" } }
      }
    },
    {
      id     = "recent-errors"
      type   = "errors"
      grid   = { x = 6, y = 0, w = 6, h = 3 }
      config = { limit = 10, sort = "last_seen_desc" }
    },
  ])
}
```

## Schema

### Required

- `project_id` (String) The project's `id`, as a project read returns it.
- `title` (String) Dashboard title

### Optional

- `default_ts` (String) Default time range. Null clears it.
- `widgets` (String) The dashboard's widgets, kept and read back in this order. Sent on an update, the list replaces the stored one. Defaults to `[]`.

- `created_at` (String) When the dashboard was created
- `id` (String) Unique identifier
- `is_default` (Boolean) Whether this is the default dashboard
- `links` (Attributes) Links into the Honeybadger web UI (see [below for nested schema](#nestedatt--links))
- `shared` (Boolean) Whether the dashboard is shared with all team members

## Notes

- **Widget ids are required.** Every widget needs an `id`, kept as written and unique within the dashboard (another dashboard can use the same id). Use letters, digits, `-` and `_`: the id appears in web UI links.
- **Set `grid` to control layout.** Left out, a widget is placed at `{x: 0, y: 0, w: 12, h: 3}`; a partial grid takes its missing keys from that. A widget moved in the web UI is put back by the next apply that writes the dashboard.
- **`streams`** left out or `[]` means every stream in the project.
- **What Honeybadger adds isn't drift.** Keys you don't set (a filled-in grid, every stream) are ignored. A value you set that changes in Honeybadger shows in the plan as the whole `widgets` string changing.
- **"Provider produced inconsistent result after apply"** means Honeybadger didn't keep a value you set, such as a stream the project doesn't have yet (just after the project is created). The dashboard is in state: fix the value, or leave it out, and apply again. A stream slug other than `default` or `internal` is refused before anything is saved.
- **Reformatting** `widgets` (key order, a heredoc instead of `jsonencode`) plans an update that changes nothing.
- **Import:** put the dashboard's widgets in your config before applying. With `widgets` left out, the default `[]` removes every widget. The first plan after import is an update that settles state to your JSON.
- **The default dashboard** can be imported. Honeybadger creates a new one the next time someone opens Insights if it's destroyed.
