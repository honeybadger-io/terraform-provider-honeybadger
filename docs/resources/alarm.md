# honeybadger_alarm (Resource)

An Insights alarm. Read from Honeybadger's copy of the alarm, written after each change; an edit made directly in the alarm service doesn't show here.

## Example Usage

```terraform
resource "honeybadger_alarm" "errors" {
  project_id        = honeybadger_project.app.id
  name              = "Error spike"
  query             = "filter event_type::str == \"notice\" | stats count() as count"
  evaluation_period = "10m"
  lookback_lag      = "1m"

  trigger_config = {
    type = "alert_result_count"
    config = {
      operator = "gt"
      value    = 100
    }
  }
}
```

## Schema

### Required

- `evaluation_period` (String) Window each evaluation covers. At least 1m and less than a week (`w` units are refused).
- `lookback_lag` (String) How far behind now the window ends, allowing for ingestion delay
- `name` (String) Alarm name
- `project_id` (String) Project public ID
- `query` (String) BadgerQL evaluated on each check
- `trigger_config` (Attributes) What turns the alarm on. Sent whole: on update, a `trigger_config` replaces the stored one rather than merging into it. (see [below for nested schema](#nestedatt--trigger_config))

### Optional

- `description` (String) What the alarm watches for, shown with it in Honeybadger.
- `stream_ids` (Set of String) Streams the query runs against. A set; can't be empty. Left out, every current stream in the project, which a read then lists. An ID that isn't one of the project's streams fails the request with 422. A set; order is ignored and duplicates are dropped.

### Read-Only

- `created_at` (String) When the alarm was created
- `id` (String) Alarm identifier (opticon observer root ID)

## Notes

- **`stream_ids`:** left out, the alarm gets the project's current streams, and state shows them. Removing `stream_ids` from config stops Terraform managing it and keeps the stored list. To change the streams, list them.
- **New projects:** a project's streams are set up just after it's created. An alarm created in the same apply, with `stream_ids` left out, waits for them. If they take longer than a few seconds, the apply fails and succeeds when rerun.
- **Trigger rules:** rules that depend on `trigger_config.type` are checked by the API when the alarm is applied, not at plan time.
- **An invalid trigger on update** is answered with success and the old trigger kept. Terraform then reports "Provider produced inconsistent result after apply".
- **Import:** an alarm whose stored copy has no trigger imports with `trigger_config` null, so the next plan adds one.
- **A create that times out** can leave an evaluator behind in Honeybadger's alarm service with no alarm attached. Check the project's alarms before applying again.
- **A retried delete can fail** if the alarm service already removed the alarm's evaluator.
- **When the alarm service is unavailable**, the API answers 503. On create, Terraform reports that the create may have succeeded and how to adopt the alarm with import.
